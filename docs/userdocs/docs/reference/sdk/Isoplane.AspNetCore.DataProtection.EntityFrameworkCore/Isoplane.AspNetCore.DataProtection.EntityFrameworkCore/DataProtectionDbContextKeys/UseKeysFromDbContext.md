# DataProtectionDbContextKeys.UseKeysFromDbContext&lt;TContext&gt; method

Keeps the Data Protection keys in the `DataProtectionKeys` table of *TContext*, as ASP.NET Core's `PersistKeysToDbContext` does, but reaching the database asynchronously, which the sandbox requires. The table has the same shape, so the application can share its keys with one hosted elsewhere.

```csharp
public static IDataProtectionBuilder UseKeysFromDbContext<TContext>(
    this IDataProtectionBuilder builder)
    where TContext : DbContext, IDataProtectionKeyContext
```

| parameter | description |
| --- | --- |
| TContext | The application's context, registered with `AddDbContext`. |
| builder | What `AddDataProtection` returned. |

## Return Value

*builder*.

## Remarks

This is `UseKeysFrom` from Isoplane.AspNetCore over the table, and behaves as it does. The keys load when initialization finishes, so the table must exist by then. An `Initialization.Initializing` callback that protects or unprotects data itself awaits `app.LoadDataProtectionKeysAsync()` first. A prepared template retains the key ring it loaded; reusing it reloads none. New initialization can load newer keys. [Keep Data Protection keys across builds](../../../../../concepts/dotnet-runtime-differences.md#keep-data-protection-keys-across-builds) describes this in full.

## Examples

```csharp
builder.Services.AddDataProtection().UseKeysFromDbContext<AppDbContext>();
```
