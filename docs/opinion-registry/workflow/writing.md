# Writing

These apply to everything written for a reader: customer and internal
documentation, code comments, reports, issues and commit messages.

## Make definitions an aid, not required reading

Write so that a reader who skips every glossary, legend and "how to read this"
section still understands the text. Give a label words that say what it means
where it appears, and explain a term the reader needs in the sentence that
first uses it. A list of definitions may still serve a reader who wants
precision: put it beside what it explains or after it, where it can be ignored.

**Not this:** A page that opens by defining "Outlook: By design" and "Impact:
None", then fills a table with those codes. A report that names its options A,
B and C and argues in letters. A comment that relies on an abbreviation
defined in another file.

**Exception:** Vocabulary the reader already has, and names the product itself
shows them, such as an error code or a setting. Link those to the one page that
defines them.
